# Vision

Kracht is a batteries-included supplement to Guile's standard library: a prelude
that re-exports the SRFIs everyone imports anyway, plus the helpers Guile's core
does not provide and every small service ends up writing twice. Its character is
set by two rules — delegate rather than duplicate, and bind values rather than
splice them. The interesting question for the next few years is how far those
rules can be pushed before the library either grows into a framework or stops
being worth importing.

## Where kracht is today

At v0.3.8 the library is seven modules and roughly 4000 lines, of which 2468 are
a generated table.

- `(kracht prelude)` — the umbrella. It re-exports SRFI-1, SRFI-2, SRFI-8,
  SRFI-11, SRFI-19, SRFI-26, SRFI-43 and SRFI-111, plus `(ice-9 match)` and
  `(ice-9 pretty-print)`, so one `use-modules` is usually enough.
- `(kracht strings)` — predicates and helpers, the UTF-8 conversions and
  `string-replace-substring` re-exported rather than rewritten, and base64 in
  pure Scheme with no shelled-out binary.
- `(kracht lists)` — `flatten-list`, an association-list toolkit (`assoc-lens`,
  `alist-set`, `assoc-ref-or`), `evaluate-thunks`, `shuffle-fy`.
- `(kracht sql)` — 746 lines: identifier and literal quoting, a condition list to
  `WHERE` compiler, and parameterised builders for `INSERT`, multi-row `INSERT`,
  `UPSERT`, `UPDATE`, `DELETE` and `SELECT`. They return a query object holding
  SQL with placeholders and the values to bind, never a statement with a value in
  it. Dialects are data: ANSI quoting or backticks, `ON CONFLICT` or
  `ON DUPLICATE KEY`, four placeholder styles plus a procedure.
- `(kracht web)` — `html-escape`/`html-unescape`, and `html-escape-context`,
  which names the *position* a value goes into (`text`, `attribute`,
  `unquoted-attribute`, `js-string`, `css-value`, `url`) rather than the
  technique, with one encoder per position.
- `(kracht html-entities)` — the data behind that: 2125 HTML5 named references
  for decoding and 253 characters willing to be written as a named entity for
  encoding, both generated by `tools/generate-html-entities.scm` from a vendored
  copy of the standard's own `entities.json`.
- `(kracht io)` — whole-file read and write, `syscall`, `getenv-or`,
  `get-short-commit-sha`, `build-asset-library`, port re-exports, and the entity
  tables' generator lives beside them under `tools/`.

The suite is three specs, about 1900 lines, run through Veritas. The project ships
four ways — the jointhefreeworld Guix channel, a Nix flake, a two-stage container
image, and Debian/openSUSE/Arch recipes — and WikiMusic, LucidPlan and Byggsteg
depend on it: three applications with no compatibility layer between them, which
is the real test of the API.

Five decisions constrain everything that follows.

1. **Re-exports are Guile's own procedures, not copies.** Nothing in that group
   is reimplemented, and the README says so. A second, subtly different
   `uri-encode` is how bugs get in.
2. **Hash tables are deliberately not re-exported.** Guile's native tables and
   SRFI-69's are different types, and swapping them breaks callers.
3. **Escaping belongs to a position, and happens last.** The library rejects the
   idea that a string can be "escaped"; only a value going into a context can.
4. **SQL is built with placeholders.** `escape-sql-string` exists for a
   hand-checked query, but the builders bind, and dialect differences are data
   rather than advice in the documentation.
5. **Data that can be generated is generated.** What kracht is willing to *write*
   as an entity is a list in the generator — a decision, not a transcription.

## The vision

1. **Every module has a contract suite, and the delegation boundary is tested.**
   Each re-export is asserted to be the standard binding rather than a lookalike,
   so the boundary the README describes is enforced by the suite, not by reading.
2. **The SQL layer expresses the statements applications actually write** —
   joins, `RETURNING`, common table expressions, `UPDATE … FROM`, and an
   `ON CONFLICT` action computed from a value — while keeping the invariant that
   no value is ever spliced into the statement text.
3. **Escaping is complete over contexts, with a published corpus.** A JSON-in-HTML
   encoder, a query-string builder that handles repeated keys, and a document
   stating the composition order, backed by portable conformance vectors.
4. **A small Guile service needs no second utility library.** Request bodies,
   cookies, form decoding and response construction join the escaping in
   `(kracht web)`, in the same style: small pure functions, no dependencies, and
   errors that name what was wrong.
5. **Releases are measured and deprecation is a ritual.** Escaping and SQL
   building are benchmarked in the suite, a supported Guile range is stated, and
   a public procedure is deprecated for a release before it is removed.

## Features that are in scope and not built yet

The code already leaves room for each of these; the hard part is named.

- **Joins and subqueries in `sql-select`.** The condition list compiles to a
  `WHERE` fragment and there is nowhere to say `JOIN`. Hard part: growing the
  condition DSL into a query algebra while refusing to become an ORM — once a
  builder knows about relations it wants a schema, and a schema wants migrations.
- **`RETURNING` and computed upsert actions.** The README states that an upsert
  cannot overwrite a column with an expression of its old value. Hard part:
  parameter numbering — every column added to the conflict action must keep
  placeholder indices aligned with the values already bound, which is why
  `sql-parameterize` is the documented escape hatch.
- **A numeric-reference policy.** `html-char-ref` returns `#f` for a character
  with no reference worth writing, so the caller decides. Hard part: the rule
  itself — when a numeric character reference beats a literal UTF-8 character.
- **Asset manifests in `(kracht io)`.** `build-asset-library` anticipates a
  static-asset map, which every web application grows by hand. Hard part: content
  hashes and cache-busting without a build step, and without making a pure file
  helper depend on the clock.
- **A driver seam.** `sql-query->values` and `sql-query->alist` are the boundary a
  driver would use. Hard part: adapters for `guile-dbi`, `squee` and
  `guile-sqlite3` without any of them becoming a dependency.
- **A version and build stamp.** `get-short-commit-sha` and `getenv-or` together
  anticipate a `/version` endpoint. Hard part: reporting something true when the
  code came from a package rather than a checkout.

## New features that would be worth having

- **A conformance corpus for escaping.** A file of input/context/expected-output
  vectors, used by the suite, printable as documentation, and portable enough
  that a Rust or Go implementation could run the same file. Escaping bugs are
  cross-project bugs, and no Scheme library publishes vectors today.
- **`(kracht time)`.** SRFI-19 is re-exported but nothing converts between
  ISO-8601, SQL timestamps and `date` values in the direction a web service
  needs; it is the most-written helper in anything that stores a timestamp.
- **`(kracht forms)`.** `application/x-www-form-urlencoded` is half-covered by
  `alist-from-url-encoded-body`; multipart bodies and `Cookie`/`Set-Cookie`
  parsing are not covered at all. Hard part: boundaries and filenames.
- **`(kracht validate)`.** Small predicates returning a value or an error record
  rather than raising, in the SQL builders' spirit of reporting misuse. Input
  handling is mostly this, written badly, once per project.
- **`kracht doctor`.** A tiny CLI reporting the Guile version, which modules load,
  which procedures are delegated to which standard module, and whether the
  generated entity tables match the vendored JSON. Cheap, and it makes
  distribution bug reports actionable.
- **Benchmarks as a suite.** Veritas already supports benchmark types, and
  escaping and SQL building are the two things a request does a thousand times; a
  number in the README stops a later refactor from being "cleaner" and slower.

## Contributions that would move the needle

1. **Escape round-trip and double-escape tests.** The README promises that
   escaping is deliberately not idempotent, which survives only if a test pins it:
   an hour of work protecting the invariant every other module rests on.
2. **Re-export identity tests.** For each name the prelude claims to pass
   through, one assertion that it *is* the standard procedure: mechanical, an
   afternoon, and it turns a documentation claim into a regression test for the
   library's central rule.
3. **The conformance corpus.** Small, high-leverage, and the only contribution
   here other implementations could adopt; it also gives the per-context encoders
   the adversarial inputs they currently only meet in production.
4. **`RETURNING` in the SQL builders.** The most-missed kind of SQL, with a
   well-understood hard part (placeholder indexing) and a design the existing
   query record already accommodates.
5. **Benchmarks in the suite.** No design decisions and no API risk, and it gives
   every later performance claim something to point at.
6. **`(kracht forms)`.** The largest of these: multipart parsing is a real parser
   and cookies have enough history to be worth getting right; best attempted after
   the escaping work, whose style it should follow.

## Compared to related projects

| Project | What it is | Where kracht differs |
|---------|------------|----------------------|
| guile-lib | a broad collection of Guile modules — SRFIs, `htmlprag`, maths, string utilities — built with autotools and shipped by distributions | kracht is smaller and curated around a prelude, has no build system beyond Guile itself, and states which procedures are delegated rather than written |
| SLIB | the classic portable Scheme library, decades old, enormous, with a registration scheme per implementation | kracht is Guile-only, dependency-free and tested; SLIB's portability costs a ceremony kracht does not want |
| SRFI-1, SRFI-13, SRFI-19, SRFI-43 | the standard libraries kracht re-exports | kracht never reimplements them, and where Guile's core already provides one — SRFI-13, records, parameters — kracht stays out of the way |
| guile-json | a JSON reader and writer for Guile | complementary: kracht has no JSON and would re-export rather than rewrite one, which is what the delegation rule demands |
| `(sxml simple)` | SXML to HTML serialisation, used by template-driven Guile projects | kracht's escaping is string-to-string and position-aware and never builds a tree, so it composes with SXML instead of competing with it |
| squee, guile-dbi, guile-sqlite3 | database drivers and connection pools | kracht produces SQL text and parameter lists and never opens a connection; the driver stays a driver |
| OWASP Java Encoder, Go's `html/template` | context-aware escaping in larger ecosystems | the idea is older elsewhere; kracht's contribution is naming the context in Scheme and generating its tables from the standard's own data |

What the others do that this could still add: guile-lib's breadth of small
utilities, `html/template`'s guarantee that a value cannot escape its context, and
the conformance corpora mature encoders publish. Where kracht is ahead and should
stay ahead: no runtime dependency beyond Guile itself, base64 without a
shelled-out binary, an escaping API that names positions instead of offering
booleans, entity tables generated from the WHATWG list including the
two-code-point references, and a SQL builder in a Scheme that binds parameters.

## In the long run

- **Guile's core will stay lean.** The helpers kracht provides are the ones a
  standard library rationally declines to own: SQL assembly, escaping by
  position, association-list ergonomics. If Guile grows them, kracht should
  shrink and re-export them — success looks like deletion, not accumulation.
- **Generated data beats transcribed data.** The entity tables were the first
  instance: 2125 entries and a rule about which characters may be written. The
  same move applies to MIME types, HTTP status texts and Unicode normalisation
  data; anything in kracht that is a table should be able to name its source.
- **Delegation is a survival strategy.** A library that wraps the platform badly
  becomes a second platform; one that wraps it thinly stays useful across
  versions. Every future module should answer "what standard procedure is this
  standing on?", and say why when the answer is none.

## Getting there from here

Start with the tests that make the existing promises explicit — escape round
trips, double escaping, and the identity of every re-export — then publish the
conformance corpus, then grow the SQL builders with `RETURNING` and joins. The web
helpers (`forms`, `time`, `validate`) follow, because they should copy the style
the escaping work establishes; `kracht doctor` and the benchmarks can happen any
time and pay for themselves in bug reports and in arguments about speed.

*This document describes intent, not commitments: the exported procedures, their
behaviour notes and the licence are the contract, and nothing here changes them.*
